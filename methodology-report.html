Methodology report · credit default prediction

Methodology and final model selection

The final prediction is a weighted average of three models. They represent each customer as aggregate statistics, a six-month sequence and a set of features interpreted through a prior learned from synthetic data. The selected components and weights were determined from out-of-fold performance.

Approach

The task is to predict the probability that a customer defaults on their next payment. Submissions are evaluated by binary log loss over 6,000 hidden customers. Since this metric evaluates probability quality rather than class labels, model decisions were based on log loss instead of accuracy or AUC.

This choice had two practical consequences. First, the classes were not rebalanced because the 22.121% positive rate reflects the population from which the test set was drawn. Rebalancing would distort the predicted probabilities. Second, every stage used the competition metric directly: the GRU trains on binary cross-entropy, LightGBM on binary log loss, and the blend weights are selected using log loss.

Every customer passes through the same five stages. The pipeline branches only during modelling, when the three learners process different representations of the same rows.

stage 1CleanUndocumented category codes collapsed: EDUCATION 0/5/6 → 4, MARRIAGE 0 → 3.
stage 2Engineer23 raw columns → 81 features: lateness history, utilisation, payment coverage, spending decomposition.
stage 3ModelLightGBM, GRU and TabPFN each trained on identical folds so predictions align row-for-row.
stage 4BlendFixed weighted average of probabilities, weights chosen by out-of-fold log loss.
stage 5EmitClip to [1e-4, 1−1e-4] and write client_id, prob_default. No other post-processing.

Placement of the data split. The competition provides a fixed train/test division, and no preprocessing step uses the target label. Cleaning and feature engineering are row-wise functions applied identically to both datasets, so they are completed before the fold split. Fitted components, including the neural network scalers, blend weights and tested calibrators, use training folds only and are evaluated on held-out rows.

Data cleaning and preprocessing

Only limited cleaning was required. The dataset contains no missing values or malformed rows, but it does contain undocumented category codes. The changes below group those codes with the closest documented category.

ColumnChangeReason
MARRIAGE code 0 → 3 The dictionary defines 1–3 only. An unknown marital status is not distinguishable from “other” for prediction purposes.
EDUCATION codes 0, 5, 6 → 4 The dictionary defines 1–4 only; 4 is already “other”. The three undocumented codes cover a small tail and behave like it.

Repayment codes. PAY_0…PAY_6 use three codes for customers who were not behind that month: −2 (no balance), −1 (paid in full) and 0 (paid the minimum). These values remain distinct in the cleaned data. During feature engineering, the lateness features use PAY.clip(lower=0) to group −2 and −1 with 0, while ever_paid_full and never_used use the original codes. This preserves both interpretations of the repayment history.

These substitutions are implemented in common.clean() and applied identically to the training and test data. datasets/train_clean.csv differs from train.csv only in 290 EDUCATION rows and 42 MARRIAGE rows, and can be regenerated with a single command. The undocumented codes were identified from the unique-value and null-count checks in 2_Column_Inspection.ipynb.

Preprocessing choices not used

Four common preprocessing steps were considered but not used. Each either offered no benefit for the selected model or would adversely affect log loss.

  • No outlier removalLarge bills and payments are genuine, and log loss punishes mis-scoring them. The heavy-tailed amount columns are handled with log1p transforms inside feature engineering instead.
  • No resampling or class weightingThe 22.121% positive rate is the rate the test set is drawn from. Rebalancing shifts predicted probabilities off the true base rate, which is precisely what log loss penalises. This is also why TabPFN runs with balance_probabilities=False.
  • No imputation of the PAY_* sentinels−1 and −2 are informative states, not missing data. They are collapsed above because they share a meaning, and separately preserved as the flags ever_paid_full and never_used.
  • No scaling for the tree modelLightGBM is invariant to monotone transforms, so scaling it would change nothing. Scaling is applied only inside models/seq_model.py, and fitted on training folds only.

SEX, EDUCATION and MARRIAGE are kept as pandas category dtype so LightGBM handles them natively; the neural models one-hot encode them, and TabPFN receives them as integer codes with their column indices declared through categorical_features_indices.

Feature engineering

common.features() transforms 23 raw columns into 81 features across six families. Most amount features are expressed as ratios so customers with different credit limits can be compared. The levels and momentum family retains absolute scale where it remains informative.

FamilyExamplesWhat it captures
Repayment history pay_max, pay_mean, n_late, n_late2plus, trend_pay, recent_late, max_late_streak, months_since_late, ever_paid_full, never_used How often, how badly and how recently the customer fell behind. recent_late weights lateness by how long ago it happened.
Credit utilisation util1…util6, util_mean, util_max, util_trend, avail_credit Balance as a fraction of the limit, and its direction. Consistently high utilisation suggests a customer short of funds.
Payment coverage payratio1…payratio5, payratio_mean, payratio_min, paid_full_months, n_zero_pay The proportion of each month’s bill paid in the following month.
Levels and momentum bill_sum/mean/std, amt_sum/mean/std, coverage_total, bill_growth, amt_over_limit, log_limit Log-compressed absolute values that retain the scale removed by the ratio features.
Spending decomposition spend1…spend5, spend_mean/max/std/trend/total, n_months_no_spend, spend_minus_paid, months_spend_gt_paid Monthly spending inferred from balances and payments; see below.
Minimum-payment behaviour min_pay_ratio_mean, min_pay_ratio_min, months_paid_about_min, months_paid_under_min Whether the customer services only the minimum due (10% assumed) — a sign of strain, especially at high balances.

Spending decomposition. This feature family produced the largest gain in the project. The dataset provides statement balances and payments but not the amount charged during each month. Monthly spending can be recovered from the accounting identity for a revolving account:

BILL_t = BILL_(t+1) − PAY_AMT_t + spend_t   ⇒   spend_t = BILL_t − BILL_(t+1) + PAY_AMT_t

A rising balance may reflect either increased spending or reduced payments, which have different implications for default risk. The existing features could not distinguish these cases. Adding the spending features improved out-of-fold log loss by 0.00046 and hidden-test log loss by 0.00173, the largest improvement in the project.

Retaining absolute scale

Every family except levels and momentum consists of ratios or counts. For example, payratio3 is the same whether a customer owes $500 or $50,000. This supports comparison across customers but removes information about the total debt and whether it is growing.

The levels and momentum features were added with the neural models because the two model types respond differently to scale. A decision tree is scale-invariant: multiplying a feature by 1,000 or applying a logarithm does not change the available splits. A neural network combines weighted inputs, so large raw values can dominate smaller ones unless the inputs are standardised. These features restore the scale information removed by the ratios in a form the neural network can use.

The sequence view

For the GRU, the same six months are also arranged as a 6-timestep × 8-channel panel, ordered from oldest to newest. The channels are repayment status, a lateness flag, bill and payment as proportions of the credit limit, log-scaled bill and payment, change in balance, and the proportion of the previous bill covered by the payment.

Feature families not retained

Behavioural payment signatures (+0.00006), spending re-supplied as an ordered GRU channel (+0.00002), interaction terms (0.00000), peer-relative credit limit (−0.00011), velocity and acceleration derivatives (−0.00024) and target encoding (−0.00052) were all tested and none reached the noise floor.

Interpretation. The successful family introduced a quantity that was absent from the raw data. The other six families recombined information that was already available and did not reach the noise threshold. This result suggested that further variations of existing features were unlikely to help.

4

Validation strategy

Validation used stratified 5-fold cross-validation across 6 fold partitions (common.folds, StratifiedKFold(5, shuffle=True, random_state=seed) with seeds 0–5). All models use the same function and seeds, keeping the out-of-fold prediction vectors aligned and directly comparable.

Three aspects of this design were particularly important.

  • A shared noise floorRepeating experiments on identical splits established that a difference below 0.0005 in out-of-fold log loss is not distinguishable from fold noise on 24,000 rows. Every result in the ledger is reported against that threshold, and no change below it was adopted on its point estimate alone.
  • Strict out-of-fold scoring for fitted stepsBlend weights, calibrators and target-derived features are evaluated only on rows excluded from fitting. This requirement was introduced after the isotonic calibration result described below.
  • A quantified limitationOOF does not fully reproduce the test-time averaging process. Each OOF row is predicted only by models that excluded it, whereas each test row receives an average across all folds. OOF can measure repeated cross-validation, but it cannot measure a model refitted on the full dataset. The leaderboard result confirmed the latter limitation: the full-data refit improved hidden-test log loss by 0.00023 while leaving OOF unchanged.

The relationship between OOF and hidden-test performance remained stable at approximately 0.4214 and 0.4098 respectively. OOF was the primary selection signal. Hidden-test results were used to assess changes that OOF could not fully represent, such as full-data refits, and to reverse the survival-model blend after it regressed on the leaderboard.

Correction to the validation protocol. Isotonic calibration initially appeared to improve log loss from 0.42136 to 0.41946. However, it had been fitted and evaluated on the same out-of-fold predictions, allowing the flexible monotonic function to fit noise in the evaluation rows. Under nested cross-validation, the result was 0.42508, the worst result in the experiment table. All subsequent fitted combiners were evaluated strictly out-of-fold, and this report uses the corrected result.

Models tested and final model selection

Ten model families were tested and three received non-zero blend weights. Each selected model represents the same customers differently, allowing the ensemble to combine complementary errors.

LightGBM

the aggregate view · weight 0.45 · OOF 0.42211 · AUC 0.79104

LightGBM uses gradient-boosted decision trees. Each new tree models errors left by the preceding trees, and the outputs of hundreds of shallow trees form the final prediction. The model receives the 81 engineered features as a single tabular record per customer.

The selected configuration is compact. A maximum depth of 4, 12 leaves and strong L2 regularisation outperformed deeper configurations across 135 tests. Recent repayment status contains most of the signal, while larger trees fitted more noise.

Hyperparameter tuning

135 LightGBM configurations were tested across three sweeps: 40 coarse configurations, 60 fine configurations and a sweep scored by blend contribution rather than standalone performance. The existing configuration, originally tuned for AUC, remained within the noise threshold; the best alternative improved log loss by only 0.00004. The GRU architecture sweep selected a smaller hidden state, two layers, heavier dropout and a faster learning rate. Its effect cannot be isolated because the change was submitted with the spending features.

Why correlation alone did not determine selection. Logistic regression had the lowest correlation with LightGBM at 0.948, yet received a blend weight of 0.00. The GRU received a weight of 0.30 despite a higher correlation of 0.983. Low correlation is useful only when the model’s differences improve the combined predictions. Correlations among the selected models were 0.983 for GRU–LightGBM, 0.990 for TabPFN–LightGBM and 0.985 for TabPFN–GRU.

Ensembling and post-processing

The final ensemble uses a fixed weighted average of the three probabilities. Meta-models and per-customer model selection were also tested. The feature-aware meta-model increased log loss by 0.00208 relative to simple averaging.

How the weights were chosen

A grid search evaluated each combination of the three weights and selected the combination with the lowest out-of-fold log loss.

  • Collect prediction vectorsEach model produced an out-of-fold probability for all 24,000 training customers, with every customer scored by a model that did not use their label during fitting.
  • Enumerate combinationsEach weight was varied in increments of 0.05, retaining approximately 230 combinations that summed to 1.
  • Evaluate each combinationFor each candidate, the three probability vectors were combined and scored against the known outcomes using log loss.
  • Select the lowest lossThe weights (0.45, 0.30, 0.25) produced the lowest OOF log loss at 0.42136.

Weight stability. LightGBM weights from 0.50 to 0.70 remain within 0.0001 of the best score, indicating a broad optimum rather than a narrow peak. This reduces the likelihood that the selected weights reflect noise in the 24,000 training rows. At the two-model stage, moving the weights halfway towards equal increased hidden-test log loss from 0.41032 to 0.41045. Weight selection still introduces some overfitting risk, but neither the response surface nor the shrinkage test showed evidence of instability.

For a customer where LightGBM says 30%, the GRU says 20% and TabPFN says 25%, the submitted probability is 0.45×0.30 + 0.30×0.20 + 0.25×0.25 = 26%. The averaging is mathematically safe for this metric: log loss is convex, so by Jensen’s inequality the loss of an averaged prediction never exceeds the average of the individual losses.

Three broader observations

  • New information mattered more than additional algorithmsSeven model families were rejected, while a feature derived from the accounting identity produced the largest gain. Retained improvements came from either adding information absent from the raw columns or reducing variance through averaging.
  • Cross-validation measured feature and averaging gains differentlyThe spending features improved OOF log loss by 0.00046 and hidden-test log loss by 0.00173. Repeated CV improved OOF but did not improve the hidden test. This difference is expected because OOF cannot measure changes to the number of models averaged for each test row.
  • Low correlation was not sufficient for inclusionThe least-correlated model received a weight of 0.00, while the GRU received 0.30 despite its higher correlation. Model disagreement improved the ensemble only when it contributed useful information.

Strengths

  • Complementary model structuresThe components use aggregate statistics, temporal sequences and a pretrained prior. Models that changed only the algorithm, without adding a useful representation, received zero weight.
  • Calibrated without post-processingProbabilities can be read as probabilities. Four independent calibration tests each concluded no adjustment was warranted, which matters for a lender setting its own risk thresholds.
  • Low prediction varianceEach prediction averages 270 cross-validated fits across six fold partitions and 11 full-data refits. The averaging step introduces no fitted parameters.
  • Customer-level interpretationThe 45%-weight LightGBM component provides SHAP attributions for individual customers, allowing its predictions to be explained by feature contribution.
  • Conservative validationThe final pipeline excludes pseudo-labelling, rank transforms and leaderboard-fitted post-processing. Adopted steps were evaluated out-of-fold.

Limitations

  • Some defaults are not explained by the available dataThe twenty largest residuals are defaulters assigned only 2–4% risk, all with clean payment histories. The variables associated with these defaults do not appear in the supplied columns.
  • Performance is weaker for one subgroupThe fairness audit found that EDUCATION="other" (387 customers, 28 defaults) is over-predicted by 61% in relative terms and has an AUC of 0.645, compared with approximately 0.79 for other groups. This heterogeneous category combines documented and undocumented codes 0, 4, 5 and 6. It is the only group for which the model performs worse than predicting the subgroup base rate.
  • Most predictive value comes from one modelLightGBM alone scores 0.42211 out-of-fold, compared with 0.42136 for the ensemble. The GRU and TabPFN improve log loss by approximately 0.0007 at the cost of 180 additional fits and two dependencies.
  • Blend weights use validation dataWeight selection introduces overfitting risk, although the broad response surface and shrinkage test reduce this concern. See §6.
  • TabPFN complicates reproductionIt requires a Prior Labs licence, an API token and a weights download, and takes approximately 50 minutes to run for a 25% blend weight.

Further work

Development ended at the submission deadline. The following experiments remained feasible but were not completed within the available time.

1  TabPFN internal ensembling

TabPFN ran with n_estimators=4, meaning it processed the data under four feature orderings before averaging. Increasing this value to 8 or 16 could improve each fit, unlike repeated cross-validation, which averages more fits at the same setting. This parameter was not tested on the final configuration.

Why not done: the run at n_estimators=4 took 3h 10m, and under 4 hours remained before the deadline with no way to submit a partial result.

Runtime note: TabPFN was run on CPU because the initial pilot assumed a possible incompatibility with Apple’s Metal backend. A later test confirmed that device="mps" works and reduced runtime from 6.8s to 4.8s on 3,000 rows, with predictions identical to floating-point precision. The full run may therefore have taken about one hour instead of three.

2  A GRU trained on more channels

The sequence model reads 8 channels per month, while the spending features enter as flattened static inputs. An ordered spending channel improved log loss by only 0.00002 in a three-partition test. Since both test arms already included static spending features, this result measures only the value of ordering. A cleaner experiment would compare against a GRU with no spending inputs.

Why not done: the measured effect was inside noise, and the cleaner experiment needs two full GRU runs at roughly 50 minutes each.

3  More TabPFN fold partitions

TabPFN carries 25% of the blend on 30 fold-fits, against LightGBM’s 90 and the GRU’s 150. It remains the least-averaged component, so it sits earliest on the variance-reduction curve where each doubling buys proportionally more.

Why not done: increasing from three to six partitions changed OOF log loss by 0.00002. The hidden-test improvement of 0.00013 also included a full-data refit, which was already part of the final pipeline.

Position at the deadline. Available evidence suggested that each remaining experiment was unlikely to improve log loss by more than approximately 0.0001, while requiring several hours to run. Further progress would most likely depend on new information derived from the data rather than additional tuning of the tested approaches.

This appendix follows one validation customer through each component of the ensemble. The customer was late in the two most recent months and carried a balance close to the credit limit.

A.1  LightGBM: combining shallow decision trees

A decision tree applies a sequence of yes/no conditions before reaching an output. LightGBM combines hundreds of these trees, each limited to a maximum depth of four.

Where the questions come from

At each node, the algorithm tests candidate thresholds across the available features and measures how much each split would reduce error. It retains the split with the greatest gain, then repeats the process for each resulting branch.

The trace below shows the first tree from one trained model. Its initial split has a gain of 2,254, compared with a maximum of 248 for the remaining splits.

This tree is one of hundreds within each of 90 LightGBM models, and its structure changes with the seed and fold. Across 30 models, the first split used PAY_0 ≤ 1.5 in 13 cases, months_since_late in 12 and recent_late in 5. Although the exact feature varies, every first split measures recent lateness. This variation occurs partly because feature_fraction=0.5 exposes each tree to only half of the features.

recent_late <= 0.75?  gain 2254   — were they late in the last two months?
├─ YES (mostly safe)  → payratio_min ≤ 0.0001?  gain 248
│   ├─ YES → bill_std ≤ 2736?      → … 4 leaves, values −1.24 to −1.27
│   └─ NO  → LIMIT_BAL ≤ 75,000?   → … 4 leaves, values −1.26 to −1.28
└─ NO (recently late) → payratio2 ≤ 0.50?  gain 130   — did they pay less

The first tree changes the log-odds by only 0.06 because the learning rate scales each tree’s output by 0.03. The second tree models errors left by the first, and later trees continue this process. The 352 contributions are added in log-odds space and converted to a probability at the end.

Interpreting the trace. The arithmetic is exact for one fitted model, but another seed or fold may route the customer through different conditions. The final LightGBM probability averages 90 models, so this trace illustrates the mechanism rather than the complete prediction.

Tree depth. A maximum depth of four allows each tree to combine at most four conditions. With 24,000 customers, deeper trees created branches covering small numbers of individuals and performed worse across the 135 tested configurations.

A.2  GRU: processing the monthly sequence

LightGBM receives one row of summary features for each customer, which removes the order of events. The GRU retains this order by processing the records one month at a time, from oldest to newest, and updating its internal state after each month.

Internal state

The model maintains 32 learned values and updates them after every month. These values have no predefined meaning; during training, the model determines which aspects of the sequence are useful to retain. They may encode patterns such as recent lateness or declining payments.

Monthly update

Each month supplies the eight channels listed in §3. Two learned gates determine how the internal state changes:

  • Update gateControls how much the current month changes the internal state. A sudden missed payment may cause a larger update than a month similar to the previous one.
  • Reset gateControls how much earlier information contributes to the update, allowing older events to have less influence after a recovery.

The gate parameters are learned from the outcomes of 24,000 customers. The bidirectional GRU reads the six months both forwards and backwards, producing two 32-value states. The backward pass lets earlier months be interpreted in the context of later events.

  month 6 (oldest)   notes ← blank, then updated by month 6
  month 5            notes revised
  month 4, 3, 2      notes revised
  month 1 (newest)   notes final    → 32 numbers forwards
  read backwards                    → 32 numbers backwards
  ──────────────────────────────────────────────────────────
  those 64 + the 81 summary features
  → two small layers of arithmetic  → 34.3%

Reason for inclusion. Consider two customers who were each late twice. One was late in the two oldest months but has since paid on time; the other paid on time until the two most recent months. Their n_late, pay_max and pay_mean values are identical, so the aggregate features cannot separate a recovery from recent deterioration. The ordered sequence provides this distinction, and the GRU received 30% of the final blend.

A.3  TabPFN: in-context prediction

TabPFN is pretrained externally and does not update its parameters on the competition data. Its operation consists of external pretraining followed by in-context prediction on the supplied rows.

Pretraining by Prior Labs

Prior Labs generated millions of synthetic datasets from varied cause-and-effect structures and noise patterns. The network was repeatedly given labelled rows and asked to predict an unlabelled row. Each training task used a different generated dataset.

This process trains the network to infer relationships from labelled examples and apply them to a new row, rather than memorising a specific dataset.

Prediction on the competition data

For each fold, TabPFN receives 19,200 training customers with their known outcomes and the customer requiring a prediction. It uses these labelled examples as context and returns a probability in one forward pass.

  in:  19,200 customers + their known outcomes
     + 1 customer needing a prediction
       ↓ one pass through the network
  out: 31.2%

The network parameters remain unchanged. The training rows act as input context, so changing those rows can change the prediction without fitting or storing new parameters.

Value on this dataset. LightGBM and the GRU learn only from the 24,000 competition rows, while TabPFN also uses patterns acquired during pretraining. It matched the tuned GRU without task-specific tuning and made sufficiently different errors to improve the ensemble.

Reproduction cost. TabPFN is external and licence-gated, requires the entire training set for each prediction batch, and becomes slower as the context grows. It took approximately six minutes per fold, compared with seconds for LightGBM.

Ensemble: 0.45 × LightGBM (81 features, 90 fits + full-data refit) + 0.30 × bidirectional GRU (6×8 panel, 150 fits + refit) + 0.25 × TabPFN (30 fits + refit, pretrained). Fixed seeds; six stratified 5-fold partitions; probabilities clipped to [1e-4, 1−1e-4] and otherwise unmodified. Out-of-fold log loss 0.42136 on 24,000 customers; 0.40982 on the 6,000-row hidden test set.
